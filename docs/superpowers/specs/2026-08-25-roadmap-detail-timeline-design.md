# Roadmap 详情弹窗与状态时间轴设计

## 背景

公开端当前通过右侧抽屉展示 Roadmap 条目详情，只能看到当前状态、创建日期、说明和票数。`roadmap_items` 只保存 `created_at` 与 `updated_at`，无法还原状态多次变化的过程。

本次改造将“查看详情”替换为居中弹窗，并在详情中加入精确到日的状态时间轴。管理端每次真正改变条目状态时，数据库自动追加不可覆盖的历史记录。公开端采用轻量读取方式：每次打开详情弹窗时查询最新历史，不启用实时订阅或定时轮询。

## 目标

- 公开端“查看详情”使用居中弹窗，不再使用右侧抽屉。
- 详情弹窗展示任务创建节点和完整状态变化时间轴。
- 日期按中国时区显示为 `YYYY-MM-DD`，不显示具体时分秒。
- 管理端通过拖拽、阶段下拉框或编辑弹窗改变状态时均自动记录。
- 状态回退或重复进入以前的阶段时保留每次变化，不覆盖历史。
- 仅修改排序、标题或说明时不产生状态历史。
- 历史数据使用现有创建时间和最后更新时间初始化。
- 保持现有公开读取、管理员写入和 RLS 权限边界。

## 非目标

- 不提供状态历史的手工编辑、删除或补录界面。
- 不为各阶段设置计划日期或截止日期。
- 不启用 Supabase Realtime、WebSocket 或定时轮询。
- 不改造管理端现有看板、拖拽和条目编辑交互。
- 不修改全局品牌色、字体或页面布局。

## 方案选择

采用“独立状态历史表 + 数据库触发器”。触发器位于所有管理端写入路径之后，可以覆盖直接更新和 `move_roadmap_item` RPC，避免依赖前端主动写历史而发生漏记。

不采用以下方案：

- JSON 历史字段：并发更新、查询、索引和权限控制更复杂。
- 通过 `updated_at` 推算：只能得知最后一次修改时间，无法保存完整变化过程。

## 数据模型

新增迁移文件和表 `public.roadmap_status_history`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `bigint generated always as identity` | 稳定排序和唯一标识 |
| `roadmap_item_id` | `uuid` | 关联 `roadmap_items(id)`，任务删除时级联删除 |
| `from_status` | `text null` | 原状态；初始或历史基线记录为 `null` |
| `to_status` | `text` | 初始状态、历史基线状态或变更后的状态 |
| `changed_at` | `timestamptz` | 实际记录时间，前端按中国时区转换到日 |

`from_status` 与 `to_status` 使用现有五种状态约束：`pending`、`approved`、`in_progress`、`completed`、`rejected`。普通状态变化要求两者不同；`from_status = null` 表示初始状态或旧数据当前状态基线。

建立 `(roadmap_item_id, changed_at, id)` 索引，保证单条任务的时间轴查询和同一时刻的稳定排序。

## 自动记录与旧数据迁移

新增 `AFTER INSERT OR UPDATE OF status` 触发器：

- 新条目插入后追加 `null → 初始状态`，时间使用条目的 `created_at`。
- 更新时仅在 `old.status IS DISTINCT FROM new.status` 时追加 `旧状态 → 新状态`。
- 状态变化时间使用经过现有 `set_updated_at` 触发器更新后的 `new.updated_at`。
- 排序、标题和说明变化不追加记录。

迁移现有条目时，每条任务写入一条 `null → 当前状态` 基线，时间使用原 `updated_at`。前端同时使用条目的 `created_at` 构造“任务创建”节点，因此不会伪造缺失的旧中间状态：

- 创建日期和最后更新时间在同一天时，归入同一个日期分组。
- 日期不同时，先显示“任务创建”，再显示“当前状态”基线。
- 迁移上线后的所有状态变化均显示真实的前后状态与日期。

## 权限与公开读取

- `roadmap_status_history` 启用 RLS。
- 新增只包含任务 ID、前后状态和日期的公开安全视图 `roadmap_status_history_public`。
- `anon` 和 `authenticated` 仅获得读取所需权限。
- 浏览器角色不获得历史表的插入、更新或删除权限。
- 触发器函数使用固定 `search_path` 和受控执行权限写入历史。
- 删除 `roadmap_items` 时由外键级联删除对应历史。

历史记录不包含管理员邮箱、用户标识、IP、投票哈希或其他敏感信息。

## 前端数据流

新增 `RoadmapStatusHistoryEntry` 类型和 `listRoadmapStatusHistory(itemId)` 查询：

1. 用户点击“查看详情”。
2. 页面立即打开详情弹窗并显示现有条目内容。
3. 弹窗根据任务 ID 查询 `roadmap_status_history_public`，按 `changed_at`、`id` 升序排列。
4. 查询结果与条目 `createdAt` 合成为时间轴，并按中国时区的自然日分组。
5. 弹窗关闭时清除当前历史状态；再次打开时重新查询，获得最新状态变化。

请求切换到另一任务或弹窗关闭后，过期请求不得覆盖当前任务的时间轴。

## 弹窗与时间轴界面

视觉延续现有页面的清晰网格风格：中性背景、无衬线字体、细边框和单一蓝色强调，不新增全局设计令牌。

- 将 `ItemDetails` 从 `Sheet` 改为 `Dialog`，保留键盘关闭、焦点管理和无障碍标题。
- 桌面端使用宽弹窗，左侧显示状态、标题、创建日期、详细说明和投票，右侧显示纵向时间轴。
- 移动端改为上下布局，时间轴位于说明之后。
- 时间轴从早到晚排列，节点显示中文状态名称和 `YYYY-MM-DD`。
- 同一天存在多个事件时共享日期分组，但每次真实状态变化仍分别展示，不丢失顺序。
- `from_status = null` 的基线若与任务创建日期同日，则与“任务创建”合成一条展示；真实状态变化记录不参与合并。
- 初始记录显示“任务创建 · 初始状态”；旧数据基线显示“当前状态”。
- 加载历史时仅在时间轴区域显示骨架。
- 查询失败时保留详情和投票，时间轴区域显示错误与“重新加载”按钮。
- 投票约束、提示语和交互保持不变。

本轮只修改公开端详情展示。管理端界面不增加时间轴入口，但所有管理端状态写入都会被数据库记录。

## 错误处理

- 历史查询失败不关闭弹窗，也不阻止投票。
- 重试只重新查询当前任务的历史。
- 未知状态值在数据映射阶段作为错误处理，不渲染错误标签。
- 空历史作为可恢复兼容状态：至少显示由 `createdAt` 生成的任务创建节点。
- 数据库触发器写历史失败时，状态更新与历史写入处于同一事务，整体回滚，避免当前状态与时间轴不一致。

## 测试策略

### 数据库测试

- 历史表、索引、触发器、公开视图和 RLS 存在。
- 匿名用户和普通登录用户只能读取，不能直接写历史。
- 新任务创建自动记录初始状态。
- 状态真正变化时追加一次记录。
- 标题、说明和同阶段排序变化不追加记录。
- 状态回退和多次切换保留全部历史并保持顺序。
- 删除任务级联删除历史。
- 旧数据迁移生成当前状态基线。

### 单元与组件测试

- API 正确映射历史记录并拒绝未知状态。
- 日期按 `Asia/Shanghai` 输出 `YYYY-MM-DD`。
- 同日事件正确分组且不合并掉状态变化。
- “查看详情”打开 `dialog` 而非侧边抽屉。
- 弹窗展示加载、成功、空数据、失败和重试状态。
- 快速切换或关闭弹窗时忽略过期请求。
- 详情弹窗中的投票行为保持不变。

### 端到端与上线验证

- 公开端点击卡片可打开详情弹窗并读取时间轴。
- 管理端拖拽、阶段下拉框和编辑弹窗变更状态后，重新打开公开详情可看到新记录。
- 桌面和移动视口均无内容溢出，键盘可关闭弹窗。
- Supabase 迁移先上线，随后发布 Cloudflare Pages。
- 最终验证 `https://telljax.com` 和 `https://admin.telljax.com`。

## 验收标准

1. 公开端详情以居中弹窗展示。
2. 每条任务至少显示创建日期，历史状态按中国时区精确到日。
3. 管理端状态变化后，重新打开详情即可看到新增记录。
4. 排序、标题和说明变化不会污染时间轴。
5. 状态回退不会覆盖或删除以前记录。
6. 历史读取公开安全，浏览器不能直接修改历史。
7. 自动化测试、类型检查、Lint 和生产构建通过。
8. 数据库迁移和两个正式域名完成生产验证。
